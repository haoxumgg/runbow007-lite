## 1. 业务背景

### 1.1 现状问题

李宁集团使用 TMS（`https://otb.lining.com`）管理干线运输订单。订单从 WMS 过账、承运商提货离厂、在途运输、实际到达、客户签收到合同完成，存在多个需要人工盯守的状态节点。实际运营中反复出现四类问题：

1. **WMS 已过账但迟迟没有离厂记录** —— 货已经在系统里出库，但承运商长时间没来提货，或提货了没回填离厂时间，导致时效考核缺数据；
2. **货已到达但运输状态没更新** —— 实际到达日期已是当天，系统里仍显示"运输在途"，下游签收、结算全部卡住；
3. **签收与合同状态不一致** —— 到达时间和签收时间已经一致（说明现场动作已完成），但客户电子签没签、或运营没把状态推到"已签收"；
4. **标记了延迟却没有填延迟原因** —— 延误订单缺少归因记录，月度复盘无法追责和改进。

这四类问题的共同点是：**数据都在 TMS 里，但没人会主动去翻**。等到发现时通常已经过了处理窗口。

### 1.2 项目目标

用一个轻量自动化工具，把上述四类异常从 TMS 导出的订单明细里筛出来，主动推送到运营飞书群，做到"异常自己找人"，而不是"人去找异常"。

### 1.3 关键约束（决定了方案形态）

| 约束 | 影响 |
| --- | --- |
| TMS 无对外 API，只能通过页面导出 Excel | 数据入口是 Excel 文件，不是接口对接 |
| TMS 后台导出任务不稳定，经常取不到数据 | 自动下载不能作为唯一入口，必须有人工上传兜底 |
| TMS 视图状态按账号共享且粘性 | 自动化会继承别人切换过的筛选条件，必须有数据合理性校验 |
| 生产服务器仅 2 GiB 内存 | 不引入 Web 框架、消息队列、独立数据库；使用 SQLite + 标准库 WSGI |
| 使用人员为内部运营，非技术人员 | 操作界面必须极简：选文件、勾规则、点按钮 |

## 4. 业务规则（核心，需逐条确认）

### 4.0 通用定义

- **时区**：全部按 `Asia/Shanghai`（北京时间）判定。
- **在途状态**：TMS 中的 `运输在途` 和 `运输在途（已离厂）` 视为同一业务状态"在途"。
- **相关单号**：飞书消息中对外展示的单号是 `相关单号`，不是内部 `订单号`；内部去重仍以 `订单号` 为准。

### 4.1 R1 — WMS 过账时效预警

| 项目 | 内容 |
| --- | --- |
| 规则名称 | WMS过账时效预警 |
| 触发条件 | `离厂时间` 为空 **且** `WMS过账时间` 不为空 **且** 当前北京时间 − `WMS过账时间` > 90 分钟 |
| 阈值来源 | `rules.wms_lead_minutes`，默认 90，可配置范围 1–1440 分钟 |
| 业务含义 | 货已在 WMS 过账，但超过 90 分钟仍无承运商提货离厂记录 |
| 消息内容 | 汇总条数 + 逐条：相关单号、箱数、已过账分钟数 |
| 去重键 | `R1 \| 订单号 \| WMS过账时间` |
| 重复提醒 | **不重复**。同一订单同一过账时间只提醒一次 |
| 代码位置 | `src/runbow007/rules.py` → `RuleEngine._rule_1` |

**待确认点**：90 分钟阈值是否符合与承运商的时效约定？是否需要按承运商或组织区分阈值？

### 4.5 去重与重复提醒规则

这是本项目最容易产生业务误解的部分，单独说明。

**两种运行模式的去重行为完全不同：**

| 模式 | 去重行为 | 设计理由 |
| --- | --- | --- |
| **网页人工上传**（当前主流程） | **不去重**。每次上传都推送本轮全部命中订单 | 人工上传是有意识的动作，操作人期望"我传了就要看到完整结果"；如果被历史记录抑制，人会怀疑工具没工作 |
| **自动任务 / CLI 真实发送** | **去重**。只推送新增或到期重提醒的项 | 自动任务每小时跑一次，不去重会造成刷屏 |

**去重模式下的详细逻辑：**

1. 首次命中 → 立即提醒；
2. R1/R2 已提醒过 → 不再提醒（因为去重键里带了时间/日期，状态变了自然产生新键）；
3. R3/R4 已提醒过且仍未解决 → 次日 09:00 之后允许再提醒一次，每天最多一次；
4. 命中项消失（问题已解决）→ 标记为 resolved；
5. 消失后 **12 小时内** 又出现 → 视为数据抖动，保留原发送记录，不会立即重新提醒；
6. 消失超过 **12 小时** 后再出现 → 视为新问题，清空发送记录，立即重新提醒。

第 5、6 条的静默期由 `rules.reopen_grace_hours` 控制，默认 12 小时。

**待确认点**：R3/R4 每天重提一次的节奏是否合适？是否需要在超过 N 天未解决时升级提醒（如 @ 更高层级）？

### 4.6 数据合理性闸门（防错发）

这是一条**因真实事故新增**的规则，业务方需要知道它的存在，因为它会导致"上传后被拒绝处理"。

| 项目 | 内容 |
| --- | --- |
| 触发条件 | 本轮解析行数 < 历史基线 × 0.5，或 > 历史基线 × 1.5 |
| 历史基线 | 最近 5 次成功运行行数的**中位数**（取中位数是为了让单次异常不污染基线） |
| 例外 | 历史基线 < 100 行时跳过该判断（小数据量下比例判断是噪声） |
| 处理动作 | **拒绝处理，一行数据都不写入数据库，不发送任何飞书消息** |
| 配置项 | `rules.min_row_ratio`（默认 0.5）、`rules.max_row_ratio`（默认 1.5），设为 0 关闭 |
| 代码位置 | `src/runbow007/pipeline.py` → `Pipeline._guard_row_count` |

**事故背景**：2026-08-17 17:33，有人在浏览器里把 TMS 视图切到一个只有 38 条的筛选条件。自动化用同一账号登录后原样继承了该视图，导出 38 条而非正常的 4750 条。当时**所有校验都通过**（页面总数 38、Excel 行数 38，完全一致），于是照常算规则、照常发飞书——R1 凭空冒出 36 个候选，R3 从 274 掉到 0，实际发出了 3 条基于残缺数据的错误提醒。

**已知副作用**：月初数据重置时行数会自然骤降，可能误触发。此时可临时调低 `min_row_ratio`。

**待确认点**：0.5 / 1.5 的比例是否合适？月初误触发的频率是否可接受？
