## 快速上手（3 分钟版）

如果你只想赶紧把今天的提醒发出去：

1. 在李宁 TMS 里创建导出任务，从**下载中心**下载 Excel（`.xls` 或 `.xlsx`）；
2. 顺手记下 TMS 页面上显示的**总条数**（如 `共 4750 条`）；
3. 浏览器打开上传页 → 登录；
4. 选择刚下载的文件；
5. **页面总条数**填上第 2 步记的数字（可以不填，但强烈建议填）；
6. 规则默认 R1–R4 全勾选，直接用即可；
7. 点「确认并推送」→ 弹窗点确定；
8. 看到绿色的「已推送飞书」和三个数字，去飞书群确认消息已到达。

**完成。** 全程不超过 1 分钟。

> ⚠️ 点了「确认并推送」就是**真的发到飞书群**，没有预览环节，也没有撤回。请确认文件是对的再点。

## 1. 系统能做什么

runbow007 帮你从 TMS 导出的订单明细里，自动筛出四类需要跟进的异常，并汇总成一条飞书消息推送到运营群。

**它不能做什么**：不能修改 TMS 里的任何数据。所有状态更新、原因填写、签收操作，仍然需要你在 TMS 里手动完成。这个工具只负责"告诉你哪些单子要处理"。

## 2. 功能清单

### 2.1 提醒规则

| 规则 | 名称 | 什么情况会命中 | 该找谁处理 |
| --- | --- | --- | --- |
| **R1** | WMS 过账时效预警 | 货已在 WMS 过账，超过 **90 分钟**还没有离厂（承运商提货）记录 | 承运商 / 调度 |
| **R2** | 今日签收提醒 | 实际到达日期是**今天**，但运输状态还是「运输在途」 | 运营（更新状态） |
| **R3** | 合同签署状态异常 | 见下方两个场景 | 见下方 |
| **R4** | 延迟无原因 | 「是否延迟」= 是，但「延迟原因」是空的 | 相关责任人（补填原因） |

**R3 的两个场景**（前提都是：实际到达时间和签收时间**已经填了且完全一致**）：

| 场景 | 具体条件 | 含义 | 该找谁 |
| --- | --- | --- | --- |
| **客户未电子签** | 状态 =「已签收」，合同状态 =「签署中」 | 我们这边签收完了，客户电子签还没签 | 联系客户 |
| **运营未操作签收** | 状态仍在途，合同状态 =「已完成」 | 合同流程跑完了，运营没把状态改成「已签收」 | 运营（改状态） |

## 3. 详细操作步骤

### 3.1 从 TMS 导出数据

1. 登录李宁 TMS（`https://otb.lining.com`）；
2. 进入**集团订单管理**；
3. 应用你需要的筛选条件；
4. **记下页面底部显示的总条数**（例如「共 4750 条」）；
5. 点击**导出**，确认导出任务；
6. 打开右上角的**下载中心**（下载图标）；
7. 等待任务变为完成，下载 Excel 文件。

> 💡 **重要**：TMS 的视图筛选是**按账号共享且粘性**的。如果有同事刚在这个账号上切换过筛选条件，你导出的可能不是你以为的那份数据。所以第 4 步记下总条数很关键 —— 系统会用它做校验。

### 3.2 登录上传页

浏览器访问（具体地址向管理员索取）：

```
http://<服务器地址>:<端口>/
```

输入账号和口令。登录成功后会跳转到上传页，会话有效期 **8 小时**。

**首次使用**：如果管理员还没改过默认账号，默认是 `admin` / `admin123456`。**必须立即联系管理员修改**。

### 3.3 上传并推送

| 步骤 | 操作 | 注意事项 |
| --- | --- | --- |
| 1 | 点击「Excel 文件」区域，选择刚下载的文件 | 只接受 `.xls` / `.xlsx`，最大 32 MB |
| 2 | 勾选提醒规则 | 默认 R1–R4 全选。只想推某一类时取消其他勾选 |
| 3 | 填写「页面总条数」 | **强烈建议填**。填 TMS 页面上显示的数字 |
| 4 | 点击「确认并推送」 | 会弹出二次确认 |
| 5 | 弹窗点「确定」 | 按钮变成「正在解析并推送…」 |
| 6 | 等待结果卡片出现 | 通常几秒钟 |

### 3.4 看懂结果卡片

处理完成后页面顶部会出现结果卡片：

| 显示 | 含义 |
| --- | --- |
| 🟢 **已推送飞书，本次提醒 N 项** | 成功，去飞书群确认 |
| 🟡 **解析完成，没有符合条件的订单，未发送飞书** | 文件正常，但没有任何异常订单。这是好事 |
| 🔴 红色错误横幅 | 处理失败，见第 6 节 |

三个核心数字：

| 数字 | 含义 | 怎么用 |
| --- | --- | --- |
| **解析行数** | Excel 里读到的订单数 | 和 TMS 页面总条数对一下，应该一致（允许 ±10） |
| **规则命中** | 触发了规则的记录条数 | 一个订单可能同时命中多条规则，所以这个数可能大于异常订单数 |
| **本次推送** | 实际发出去的提醒条数 | 网页上传时通常等于「规则命中」 |

展开「查看运行详情」还能看到：文件名、各规则分别命中多少、完成时间、**运行编号**（排查问题时报给管理员用）。

### 3.5 确认飞书消息

去运营飞书群检查，消息应该是一条标题为 **「R1–R4订单提醒汇总」** 的富文本，结构如下：

```
请关注以下相关单号：
【R1｜WMS过账时效预警】
共 3 单，离厂时间为空且WMS过账已超过配置阈值。
- 相关单号 XXX｜箱数 12｜WMS过账已 145.3 分钟，仍无离厂时间
...
【R2｜今日签收提醒】
无符合条件订单。
【R3｜合同签署状态异常提醒】
【客户未电子签】
总共 8 个订单，总共 96 箱。
- 相关单号 XXX｜箱数 12
...
【运营未操作签收】
提醒内容：共 2 个订单。
- 相关单号 XXX
请运营人员将状态更新为「已签收」，合同状态为「已完成」。
【R4｜延迟无原因提醒】
综合统计：共 5 个订单。
明细：
- 相关单号 XXX
请督促相关人员及时填写延误原因，确保延误订单有完整的归因记录。
```

**没有命中的规则也会出现在消息里**，显示「无符合条件订单」—— 这是有意设计的，让群里能确认这一轮确实检查过了这条规则。

## 4. 权限说明

### 4.1 当前权限模型

系统采用**单账号共享登录**，没有角色区分。

| 事项 | 说明 |
| --- | --- |
| 账号数量 | 1 个，全体使用人员共用 |
| 权限区分 | 无。登录后即可执行全部操作 |
| 会话有效期 | 8 小时（可配置 5 分钟–7 天） |
| 登录失败限制 | 同一 IP 连续失败 **5 次**后，暂时拒绝约 **15 分钟** |
| 网络访问限制 | 服务器安全组只向可信办公出口 IP 放行，外网无法访问 |
| 操作留痕 | 每次登录、每次上传都会记入服务器日志（含来源 IP、账号、文件名） |

### 4.2 使用纪律

| 要求 | 原因 |
| --- | --- |
| **不要把访问地址和口令发到外部群或个人微信** | 页面本身不是 HTTPS，凭据泄露风险高 |
| **口令由管理员统一保管和轮换** | 单账号模式下，个人保存口令等于扩散凭据 |
| **上传前确认文件来源** | 上传即发送，没有预览和撤回 |
| **不要在多人同时操作** | 系统会拒绝并发请求，且重复上传会重复推送 |
| **发现推送内容异常立即通知管理员** | 可能是 TMS 视图被切换导致的数据问题 |

### 4.3 管理员额外能力

管理员（有服务器 SSH 权限的人）可以：

| 能力 | 命令 |
| --- | --- |
| 查看服务状态 | `sudo systemctl status runbow007-web.service` |
| 查看容器日志 | `sudo /opt/runbow007/scripts/web-alinux3.sh logs 200` |
| 重启服务 | `sudo systemctl restart runbow007-web.service` |
| 修改账号口令 | 编辑 `/etc/runbow007/secrets.env` 后重启 |
| 生成口令哈希 | `docker compose run --rm app --config /app/config.yaml web-password` |
| 命令行演练（不发送） | `runbow007 --config config.yaml process-file <文件> --rules R1,R3,R4` |
| 开关自动下载定时器 | `sudo /opt/runbow007/scripts/timers-alinux3.sh on\|off\|status` |

## 5. 常见问题 FAQ

### 使用类

**Q1：我需要每天固定时间上传吗？**
不强制。当前是人工触发模式，按运营节奏来即可。建议参考原定的自动调度节奏：R1/R3/R4 每小时看一次，R2 每天下午 13:30 前后看一次。

**Q2：同一份文件传两次会怎样？**
会**重复推送**两次完整内容。网页上传**不做历史去重**——每次上传都推送本轮全部命中订单。所以不要"手抖再传一次"。

**Q3：为什么设计成不去重？**
因为人工上传是有意识的动作。你刚下载文件、登录、勾规则、点确认，如果因为"昨天已经提醒过"只推 2 条，你会怀疑工具坏了。人工触发的语义就是"我要看到这一轮的完整结果"。

**Q4：「页面总条数」不填行不行？**
可以，是选填。但填了系统会拿它和 Excel 实际行数比对，能挡住"导出的不是你以为的那份数据"这类问题。**建议每次都填。**

**Q5：填了总条数但和实际差了几条，会失败吗？**
允许 **±10** 条的差异（读取页面总数到 TMS 生成导出之间订单还在增减，这属于正常漂移）。超过 10 条才会拒绝。

**Q6：一个订单同时命中多条规则怎么算？**
「规则命中」按**条数**统计，所以同一个订单可能被计 2 次甚至更多。飞书消息里它会出现在对应的每个规则段落下。

**Q7：为什么消息里显示的是「相关单号」不是「订单号」？**
对外沟通用相关单号更直观。系统内部用订单号做去重，两者是不同的字段。

**Q8：可以只推给某个人吗？**
不能。当前只支持推送到一个固定的飞书群。如需 @ 特定负责人，可由管理员配置 `mention_user_id`。

**Q9：能改成自动定时跑吗？**
自动下载能力代码里还在，但 **TMS 后台导出经常取不到数据**，所以定时任务默认关闭。等 TMS 导出稳定后可由管理员打开。

**Q10：手机上能用吗？**
页面是响应式的，手机浏览器可以打开。但需要先从 TMS 下载文件，手机上操作不便，建议用电脑。

**Q11：文件多久会被删掉？**
上传的临时文件在请求结束后立即删除。归档副本保存在服务器 `downloads/` 目录，默认保留 30 天。

**Q12：我能看到历史推送记录吗？**
页面上看不到。所有记录都在服务器的 SQLite 数据库和日志里，需要时向管理员索取。

### 数据类

**Q13：Excel 的表头能改吗？**
不要改。系统认识以下几组别名：订单号/订单单号、所属组织/执行组织、离厂时间(承运商提货时间)/离厂时间、是否延迟/是否延误、延迟原因/延误原因、承运商时效/配送时效、明细单总数/订单数量。**除此之外的表头改动都会导致解析失败。**

**Q14：可以手工在 Excel 里删几行再上传吗？**
技术上可以，但**强烈不建议**。删行会触发行数合理性检查，且提醒结果会不完整。如果只想推部分规则，用规则勾选，不要改数据。

**Q15：R1 一直是 0 条，是不是坏了？**
不一定。R1 需要同时满足「离厂时间为空」和「有 WMS 过账时间」。如果你的筛选条件把这类订单排除掉了，R1 自然恒为 0。系统每次运行都会在日志里记录各规则的前置条件计数，管理员可以据此判断是数据本身没有命中，还是取数口径把这些单子过滤掉了。

**Q16：R3 命中数突然从 274 掉到 0，正常吗？**
**不正常，立即联系管理员。** 这通常意味着数据集不对（比如 TMS 视图被切换了）。系统有行数闸门会挡住这类情况，但如果闸门被绕过或阈值不合适，可能会漏。

## 6. 异常处理

### 6.1 页面错误提示对照表

| 错误提示 | 原因 | 你该怎么做 |
| --- | --- | --- |
| **账号或密码不正确。** | 输错了 | 确认账号口令；连错 5 次会被锁 15 分钟 |
| **登录失败次数过多，请 N 分钟后再试。** | 触发限速 | 等待提示的时间，或联系管理员确认口令 |
| **请选择要上传的 Excel 文件。** | 没选文件就提交 | 选择文件后重新提交 |
| **只支持 TMS 导出的 .xls 或 .xlsx 文件。** | 文件格式不对 | 确认下载的是 Excel，不是 CSV/PDF |
| **上传的文件是空的。** | 0 字节文件 | 重新从 TMS 下载 |
| **上传内容超过 32 MB 上限。** | 文件过大 | 联系管理员调高上限，或缩小导出范围 |
| **请至少勾选一条规则。** | 全部取消勾选了 | 至少勾一个规则 |
| **页面总条数必须是数字。** / **必须大于 0。** | 填了非法值 | 填正整数，或留空 |
| **会话已过期，请重新提交。** | 页面开太久，CSRF 令牌失效 | 刷新页面重新登录后再传 |
| **已有任务正在运行，请稍后再试。** | 有人正在上传，或定时任务在跑 | 等待几十秒后重试。**不要连续猛点** |
| **缺少必要表头: XXX** | Excel 缺列 | 检查是否用了正确的 TMS 导出模板 |
| **订单号重复: XXX（第 N 行）** | Excel 里有重复订单号 | 重新从 TMS 导出；如仍重复，报管理员 |
| **第 N 行订单号为空** / **相关单号为空** | 数据不完整 | 重新导出；如仍有空行，报管理员 |
| **第 N 行 XXX 无法解析: YYY** | 时间格式不认识 | 不要在 Excel 里改过时间格式；重新导出 |
| **第 N 行 是否延迟 值未知: XXX** | 布尔值不认识 | 只接受 是/否/true/false/1/0/yes/no |
| **页面显示 N 条，但 Excel 有 M 个唯一订单** | 总条数与文件不符超过容差 | 见 6.2 |
| **本轮解析到 N 行，相对最近几次成功运行的中位数…** | 行数合理性闸门拦截 | 见 6.3 ⚠️ **重点** |
| **飞书发送失败: CODE MSG** | 飞书接口报错 | 见 6.4 |
| **服务内部错误，请查看日志。** | 未预期的异常 | 记下时间，联系管理员 |

### 6.2 「页面显示 N 条，但 Excel 有 M 个唯一订单」

**含义**：你填的总条数和文件实际行数相差超过 10 条。

**排查顺序**：

1. 是不是总条数记错了？回 TMS 确认；
2. 是不是下载了**旧的**导出任务？下载中心里可能有多个任务，确认下的是最新那个；
3. 是不是在 Excel 里删过行？
4. 是不是 TMS 视图被同事切换过？重新在 TMS 里确认筛选条件，重新导出。

**临时绕过**：把「页面总条数」留空再传。但这样就失去了这道校验，**只在你确信文件正确时才这么做**。

### 6.3 ⚠️ 「本轮解析到 N 行，相对最近几次成功运行的中位数 M 行不足 50%」

**这是最需要认真对待的一条。**

**含义**：这份文件的行数和最近几次比明显不对劲，系统怀疑数据不完整，**已经拒绝处理，一行数据都没进库，也没发任何消息**。

**这道防护为什么存在**：2026-08-17 曾经发生过真实事故 —— 有人在浏览器里把 TMS 视图切到一个只有 38 条的筛选，自动化用同一个账号登录后原样继承，导出了 38 条而不是 4750 条。当时**所有校验都通过了**（页面总数 38、Excel 行数 38，完全一致），于是照常算规则、照常发飞书，真的发出了 3 条基于残缺数据的错误提醒。这道闸门就是为了堵这个口子。

**你该怎么做**：

1. **不要试图绕过它。** 先弄清楚为什么行数不对；
2. 回 TMS 检查筛选视图是不是被切换了 —— 特别是「AI导出数据（勿动）」这个预设；
3. 确认视图正常后，重新导出、重新下载、重新上传；
4. 如果确认数据本身就是对的（比如**月初数据重置**导致订单数天然骤降），联系管理员临时调整阈值。

**误报场景**：月初数据重置时订单量会自然大幅下降，这是已知的误报来源，属于正常现象。

### 6.4 「飞书发送失败」

**含义**：数据处理完成了，但消息没发出去。系统已经自动重试了 3 次。

**排查**：

1. 飞书开放平台是否有故障公告？
2. 联系管理员检查 App Secret 是否过期、机器人是否还在群里、群 ID 是否变了；
3. 修复后**重新上传同一份文件**即可（网页上传不去重，不会因为"上次失败过"而跳过）。

### 6.5 页面完全打不开

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 浏览器超时/连接被拒 | 服务未运行，或你的 IP 不在安全组白名单 | 联系管理员 |
| 502 / 504 | 反向代理层问题（如果有） | 联系管理员 |
| 打得开但一直转圈 | 正在处理大文件 | 等待；超过 2 分钟联系管理员 |

**管理员排查步骤**：

```bash
# 1. 服务状态
sudo systemctl status runbow007-web.service

# 2. 容器状态
sudo /opt/runbow007/scripts/web-alinux3.sh status

# 3. 健康检查
curl http://127.0.0.1:18080/healthz     # 应返回 ok

# 4. 最近日志
sudo /opt/runbow007/scripts/web-alinux3.sh logs 200
sudo tail -n 200 /opt/runbow007/logs/runbow007.log

# 5. 重启
sudo systemctl restart runbow007-web.service
```

### 6.6 飞书群里收到了内容明显不对的提醒

**立即行动**：

1. 在群里 @ 管理员，说明"这条提醒的数据不对"；
2. 附上上传页结果卡片里的**运行编号**（如果是你上传的）；
3. 让管理员核对 `downloads/` 目录里对应的归档 Excel；
4. **在问题澄清前，不要重复上传**。

**管理员核对方法**：每次运行都记录了文件的 SHA-256、行数、各规则命中数，可以和当时的归档文件逐一对上。

### 6.7 收到「runbow007 运行失败」告警

这是**自动定时任务**失败时发出的告警（当前定时任务默认关闭，正常不应出现）。

消息格式：

```
runbow007 运行失败
服务：runbow007-hourly.service
自动任务执行失败，请检查服务器日志。
摘要：Result=... ExecMainStatus=... ...
```

**运营人员无需处理**，由管理员查服务器日志。如果频繁出现，说明自动下载不稳定，应确认定时器是否被误开启。

## 7. 附录：飞书消息中的特殊表述

### 7.1 「当前符合条件共 N 个订单；以下为本轮新增或到期重提醒的 M 个订单，另有 K 个此前已提醒」

**只在自动任务/CLI 模式下出现**（网页上传不去重，不会有这句）。

含义：这条规则当前一共有 N 个订单符合条件，但其中 K 个之前已经提醒过了，这次只列出 M 个新的。**问题总数是 N，不是 M。**

### 7.2 「当前仍有 N 个符合条件订单；本轮无新增提醒（此前已提醒）」

含义：问题还在，只是这一轮没有新增。**不代表问题已解决。**

### 7.3 「无符合条件订单。」

含义：这条规则这一轮确实没有任何命中。这是好消息。
